## 2. The analysis (done, real frame extraction)

X blocks yt-dlp; the phone has no ffmpeg. Solved by:
- `https://api.fxtwitter.com/<user>/status/<id>` gives the direct mp4 (712x1276, 123.67s, 1.5Mbps,
  H.264 High@3.1). Saved to `/sdcard/Download/Gk0nar_HTFDybwbi.mp4` (25.3MB).
- Built an in-process ffmpeg decoder: downloaded the merged `libffmpeg.so` (FFmpeg 9.0, arm64,
  all 7 modules static-linked, 80MB) from **hzw1199/Android-FFmpeg-Prebuilt** and dlopen'd it via
  libc, binding avformat/avcodec/sws_scale by ctypes. **This is the reusable asset of the session.**

Working decoder lives in `files/ffpy/`:
| file | role |
|---|---|
| `frames.py` | dlopen + Video class, decodes to RGB24 via sws_scale |
| `sampler.py` | seek-based frame grab (stream timebase is 1/1536000, NOT 1/90000) |
| `util.py` | fast JPEG encode via Android Bitmap; lum signatures |

Traps already paid for (do not rediscover):
- `av_frame_unref` must come AFTER the RGB copy, or every frame reads as zeros.
- `sws_getContext` caching had a bug where `_fmt` was set before comparing — context never built.
- RGB->ARGB via per-pixel `struct.pack` = 48s/frame. The fast path is bytearray interleave
  (`buf[0::4]=0xff...; buf[1::4]=rgb[0::3]...`) then one `struct.unpack('<%di')` = 0.06s.
- `create_string_buffer` must be kept alive on self or the sws destination is freed.

Measured findings fed to the user:
- 7–12% duplicate frames at every sample point (sawtooth: ~3.5 delta baseline, drops to ~0.4).
- Inter-frame delta 2.3–7.6 luminance/255 — low-amplitude drift, reads as floaty not weighted.
- Krishna's blue-skin pixel share: 9.3% at t=0, 8.3% t=12, then **0.0% for 44 straight seconds
  (t=32–76)**, returning at 108s (13.1%) and 120s (16.3%).
- Beat map: 0–11 courtyard / 11–27 Krishna centred / 27–42 hard cut to forest, Hanuman meditating /
  42–75 the challenge / 75–108 finger-to-ground / 108–124 Krishna close-up.

## 3. The correction the user made (important)

I first answered with screen-time/framing numbers. User corrected: it's about **presence inside the
shot**, not screen share. The real diagnosis, from reading the actual frames:
- Krishna is **performing at the camera** — brows up, mouth open mid-word, head tilted to charm,
  hands explaining. Hanuman in the same shots sits still, heavy, and never asks for attention.
- Hanuman reads divine because his default prior is stillness; Krishna's is charm. **The engine was
  faithfully reproducing priors — nothing in the pipeline fought for Krishna.**
- The missing thing is *interiority*: a god never asks. Presence lives in the beat where the face
  decides whether to respond.
- Light: Krishna is lit at the same value/fill as Balarama beside him, so the eye reads "costumed
  colleague". A divine figure is never lit as a peer.

  duplicate-heavy and over-busy.

Calibration number that matters: `motion_texture` (coefficient of variation of non-artefact
deltas). Flat drift 0.00 · the real footage 0.06–0.15 · articulated performance 0.32–0.62.
Thresholds set at 0.15–0.18. The first accent detector was WRONG (fired on recovery from a
duplicate zero); fixed by comparing only above a floor.

## 9. Production rules encoded in the repo (the actual answer to "ship 500 episodes")

1. Direct the still, then animate the still — presence review belongs on the keyframe.
2. Gate before retry; never retry unattended (cost control).
3. Hold longer than the model wants: generate 4s, keep best 2s, retime 80%, cut before drift.
4. Two grades — hero shots strict, coverage loose. 500 episodes all-hero is impossible.
5. Sound carries more presence than picture.
